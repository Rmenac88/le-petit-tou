## 1. Notifications personnalisées

| Type | Déclencheur | Titre | Texte | Canal Android | iOS | Image (Android) |
|---|---|---|---|---|---|---|
| Événement | ajout dans `events` | 🎉 Nouvel événement | titre + « — le JJ/MM » | `lpt-events` « Événements » | sous-titre « Événements de l'association », importance normale, regroupement `event` | image de l'événement |
| Agenda | date active ajoutée | 📅 À l'agenda | titre — JJ/MM | `lpt-agenda` « Agenda des partenaires » | sous-titre, regroupement `agenda` | — |
| Nouvelle adresse | adresse `is_new` | ✨ Nouvelle adresse | nom | `lpt-new-spots` « Nouvelles adresses » | importance « discrète », regroupement `new_spot` | image de l'adresse |
| Plusieurs adresses | regroupement serveur | ✨ N nouvelles adresses | « Découvre les nouveautés… » | `lpt-new-spots` | idem | aucune (une seule photo ne doit pas illustrer un groupe) |
| Annonce admin | portail | 📣 + titre saisi (sauf s'il commence déjà par un émoji) | message | `lpt-announcements` « Annonces », importance haute | sous-titre « Message du Petit Tou » | — |

- **Android** : icône blanche en cœur (96 px, déjà présente sur la branche `main` de l'équipe, copie identique pour éviter tout conflit), couleur d'accent `#E84A5F` (plugin `expo-notifications`, vérifié par un prébuild : ressources générées dans toutes les densités), canal par défaut déclaré, 5 canaux regroupés sous « Le Petit Tou » dans les réglages du téléphone, vibration et lumière aux couleurs de la marque.
- **iOS** : le système n'autorise ni couleur d'accent ni icône par notification (c'est l'icône de l'appli). Ce qui est personnalisé : émoji, sous-titre, regroupement par type, niveau d'importance. **L'image n'est pas affichée sur iOS** : elle exige une extension native (« Notification Service Extension ») que je n'ai pas ajoutée.
- **Compatibilité** : un canal inconnu du téléphone fait **disparaître** la notification. Le serveur n'utilise donc les canaux par type que pour les téléphones dont l'appli l'a annoncé à l'inscription (`channels_v2`) ; les autres reçoivent sur « default ».
- **Aucune donnée personnelle** dans les messages (test automatique) : titre, texte, image publique d'un établissement, identifiant public.
- **Corrections trouvées en route** : l'identifiant d'une annonce dérivait de l'horloge (deux annonces dans la même fraction de seconde s'entrechoquaient : la seconde échouait) → identifiant aléatoire ; une expression de validation d'image dépassait la limite de PostgreSQL (repéré par les tests avant tout déploiement).

## 2. Les chouchous du Petit Tou

- **Accueil** : nouvelle section tout en bas (après les événements, avant le pied de page) : cartes avec badge « ♥ CHOUCHOU DU PETIT TOU », note, catégorie, mention facultative, cœur de like, fiche détaillée au toucher. Masquée s'il n'y a rien. Dernière liste connue gardée localement (affichée dès le lancement, même hors connexion) puis rafraîchie ; revérifiée avec la date du téléphone.
- **Portail** : onglet « Chouchous du Petit Tou » : recherche rapide (sans accents, tous les mots, quartier/adresse/étiquettes), bouton **Ajouter** en un appui (en ligne tout de suite, en dernière position), puis modification : mention (40 caractères), ordre, début/fin d'affichage (jours inclus), masquer/afficher, monter/descendre, retrait avec confirmation. L'accueil se met à jour immédiatement.
- **Base** : `featured_spots` (RLS : la clé publique ne lit que les lignes actives dans leur période ; aucune écriture directe) + `admin_list_featured`, `admin_save_featured`, `admin_delete_featured` protégées par le code admin (même verrouillage anti force brute que le reste). Validations côté serveur : adresse existante, doublon, mention, ordre, dates réelles, fin ≥ début, identifiants illisibles.

## 3. Fond de l'accueil personnalisable

- **Accueil** : le bandeau garde Galaxy par défaut ; une image choisie dans le portail le remplace (fondu), avec un voile violet qui garde le texte lisible. **Repli automatique sur Galaxy** si l'image est introuvable ou illisible, ou si aucun réglage n'existe. Réglage mémorisé localement (pas d'attente réseau au lancement).
- **Portail** : onglet « Apparence » : fond actuel, choix d'une image (sélecteur système, aucune autorisation de galerie requise), aperçu, contrôle du type et de la taille avant envoi, bouton **Afficher sur l'accueil**, bouton **Revenir au thème Galaxy**.
- **Sécurité de l'envoi** : le portail demande un **billet** (code admin vérifié côté serveur) fixant le chemin exact du fichier, valable 10 minutes, un seul fichier. Le stockage n'accepte un envoi dans le dossier `app-backgrounds` qu'avec un billet valide, via une politique **restrictive** qui s'applique même si une ancienne politique grande ouverte existe en production ; modifier ou supprimer un fichier de ce dossier est interdit à la clé publique. Dossier public en lecture, 2 Mo, JPEG/PNG/WebP ; `admin_set_home_background` revérifie taille et type du fichier réellement reçu. 20 billets en attente au plus.
- **Limite connue** : les anciennes images restent dans le dossier (Supabase interdit la suppression directe en SQL) ; ≤ 2 Mo chacune, seul l'admin peut en ajouter.
- **Contrôle par sabotage** : j'ai retiré volontairement chacune des trois protections (politique restrictive d'envoi, interdiction de modification, vérification du billet) : les tests échouent à chaque fois.

## Ce qui nécessite un nouvel APK
Tout côté application : canaux et icône de notification, section chouchous, fond d'accueil, onglets du portail. **Un seul build** couvre les trois chantiers.

## Ce qui nécessite d'appliquer une migration en production (accord de l'utilisateur requis)
010 (style des notifications), 011 (chouchous), 012 (fond d'accueil). **Appliquées en production le 24/10/2026** avec l'accord de l'utilisateur (un seul collage dans l'éditeur SQL, sans erreur). Contrôles faits ensuite avec la seule clé publique : `featured_spots` et `app_settings` lisibles (vides), `upload_tickets` illisible (401), les trois fonctions admin refusent un mauvais code, `register_push_token` à 7 paramètres répond (plus de 404), un envoi dans `app-backgrounds` sans billet est refusé par la politique de stockage (403), le dossier existe, `scripts/audit-prod-check.sh` : tout est conforme. Restent à vérifier sur appareil : l'affichage des notifications, l'envoi d'une vraie image depuis le portail.

## Ce qui n'a pas pu être testé sur un appareil réel
- L'affichage réel des notifications (émoji, icône blanche, couleur, canaux dans les réglages Android, image, regroupement iOS).
- Le sélecteur d'image du portail et l'envoi réel vers le stockage Supabase (simulé en base locale ; le stockage réel et son interface n'étaient pas disponibles).
- L'effet visuel du fond personnalisé sur de vrais téléphones (le voile est fixe : des images très claires peuvent donner un contraste moyen).
- Le rendu de la section chouchous sur Android/iOS (vérifié sur le web uniquement).
